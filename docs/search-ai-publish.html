Search, AI, and Publishing

Current AI Entry Points

The current app splits AI into two surfaces: the Today conversation, where user text is first written into the daily HTML note before AI replies, and the note sidebar, where AI can summarize, suggest titles, and extract tags.

Model configuration is kept in Settings rather than exposed in the note sidebar. Settings supports provider choice, custom API base URL, model name, API key, explicit saving, model connectivity tests, and model fetching.

This keeps AI from becoming a plain chat shell: the user's raw expression becomes a local file first, and AI continues from that durable record.

AI Editor Tool Protocol

The editor now has a command layer that toolbar actions can use, and the same layer can be exposed to future AI note-writing flows. AI should receive tool descriptors, not raw editor internals.

  • Each command has an id, localized label key, category, availability check, optional payload schema, and AI metadata.
  • AI-visible metadata records whether a command mutates the note, which permission it needs, whether confirmation is required, and whether a history snapshot should be created.
  • An AI operation plan can be previewed before execution, including unknown commands and whether the plan changes local notes.
  • Execution can create a local history snapshot first and restore the original editor HTML if a command fails.

This is groundwork. It does not mean AI can silently rewrite notes. User-visible confirmation, source display, and local history remain part of the safety model.

中文概要

这一页说明搜索、AI 和发布的关系。普通搜索解决关键词和结构检索，AI 搜索解决用户不记得旧文档怎么写、但想恢复上下文的问题。

当前也加入了 AI 编辑工具协议的基础结构：AI 未来应通过 Opaline 编辑命令层生成操作计划，而不是直接改 HTML 字符串。

发布功能应该分阶段：先静态导出，再托管发布，最后才是公开知识网络。读者选中文本后搜索作者公开笔记，是长期差异点，不是第一版功能。

  • 精确搜索负责快速找到关键词、标题、标签和路径。
  • 结构化搜索负责按元数据、链接、时间和状态过滤。
  • 语义搜索负责找到“意思相近但词不一样”的旧笔记。
  • AI 回答必须带引用、能回到原文，并且区分事实和推断。

公开发布的重点不是把文章丢到网上，而是让公开知识库可以被读者继续搜索、理解和追问。

Before Semantic Search: What Keyword Search Already Solves

A fair question: if SQLite FTS5 can search thousands of notes in milliseconds, and I wrote these notes myself so I mostly remember the keywords — do I even need embeddings or AI search?

For personal use, keyword search with good filtering solves more than it gets credit for:

  • You remember a project name → title search finds it instantly.
  • You remember a technical term → body search with FTS5 is sub-millisecond.
  • You remember roughly when you wrote it → time-range filter narrows to 5 candidates.
  • You remember it linked to another note → mentions surface it immediately.

The limits of keyword search become real when:

  • You remember the conclusion but not the words you used. ("That note about why we picked Postgres over MySQL" — but the note never says "picked" or "over.")
  • You wrote something years ago and your vocabulary has shifted.
  • Someone else is searching your published notes and doesn't know your naming habits.

This is why the roadmap puts semantic search after keyword search, and reader-facing concept search even later. The 80/20 is: keyword search for yourself, semantic fallback for when keywords fail, and RAG as the killer feature for readers of published knowledge.

Search should help users recover old context, not only match keywords.

Exact Search

Fast local keyword search across titles, headings, body text, tags, and paths. This is the enhanced Ctrl+F layer.

Structured Search

Filters over path, tag, note type, created time, updated time, linked notes, and broken links.

Semantic Search

Optional AI or embedding-powered retrieval over local notes. The result should show matching notes and snippets before generating any answer.

AI Answers

AI should answer only with visible sources.

  • cite notes
  • link back to original text
  • show retrieved snippets
  • say when no relevant note was found
  • separate source facts from AI inference

Private notes should not be sent to cloud models without explicit user permission.

RAG Architecture and Pitfalls

Opaline's format gives RAG a structural head start: every block already has a stable ID, language metadata, and semantic element type. But architecture that looks clean on paper still has real pitfalls. This section documents them so they are designed around, not discovered late.

Why Opaline's Format Helps RAG

  • Blocks are pre-chunked. A <section data-opaline-block> or <p id="..."> is a retrieval unit defined by the author, not by a sliding window. Author-defined boundaries beat algorithmic chunking every time.
  • Stable IDs survive edits. When a note is reorganized, the block ID stays attached to the same content. Citations don't drift.
  • Language metadata routes embeddings. A lang="zh" block goes to a Chinese-tuned embedding model. A lang="en" block goes to an English one. Mixing languages in one embedding vector degrades retrieval quality.
  • Tags and links provide structured pre-filtering. Before any vector search, filter by tag or linked-note to cut the candidate set by 90%. This is faster and more precise than pure vector search over the entire workspace.

Pitfall 1: Block Size Drift

If data-opaline-block is defined as "one retrieval unit," then block size directly determines retrieval quality. A 5000-word block will match everything and answer nothing. A single-sentence block loses surrounding context. The rule must be enforced early: one block contains one answerable idea — typically 50 to 300 words. The editor should discourage very long blocks and very short ones (except intentional one-liners like definitions).

Pitfall 2: Embedding Model Lock-In

Embedding vectors are model-specific. Switch from text-embedding-3-small to bge-m3 and all existing vectors become garbage — they were produced by a different geometry. Since embeddings live in SQLite and are marked rebuildable, this is survivable. But the rebuild cost is real: 10,000 blocks × API latency is not instant. Plan for a "rebuild all embeddings" command from day one, and prefer embedding models with stable long-term availability.

Pitfall 3: The Private-Cloud Boundary

Embedding generation and answer generation are separate steps, but both may hit cloud APIs. A user who marks a note as private must be able to trust that its content never leaves the machine. This means:

  • Embedding must support a local-only mode (e.g., ONNX model via sqlite-vec or fastembed).
  • AI answer generation must either run locally or explicitly prompt the user before sending retrieved private snippets to a cloud model.
  • The privacy boundary must be visible in the UI — a note marked private should show a clear indicator that it is excluded from cloud operations.

Pitfall 4: Citation Fragility Under Note Moves

A block ID like b-db-choice is stable within a note. But if the note is renamed or moved, the href path in links pointing to it breaks. The ID stays valid, but the URL doesn't. This means citations must resolve through ID lookup (SQLite resolves ID → current path), not through raw href. Every AI citation should store the block ID as the canonical reference and resolve the display path at render time.

Pitfall 5: Hybrid Search Is Not Optional

Pure vector search produces fluent-looking but substantively wrong results often enough to erode trust. A query like "PostgreSQL JSONB performance" should match blocks that literally contain those terms, not blocks that are semantically adjacent. The retrieval pipeline must combine:

  • Keyword match (FTS5) for precision on known terms.
  • Vector similarity for recall on conceptual matches.
  • Metadata filtering (tag, date, link) applied before either.
  • Re-ranking of combined results before they reach the LLM.

Pitfall 6: Re-ranking Budget

Retrieval might return 50 candidate blocks. Most LLM context windows can't fit 50 blocks plus the user's question plus the answer. A re-ranker (cross-encoder or smaller model) must trim this to the top 5–10 before generating the final answer. This step is easy to skip in a prototype and immediately necessary in production.

Recommended Stack for Phase 5

  • sqlite-vec for vector storage alongside FTS5 in the same SQLite database.
  • A stable embedding model with a local fallback (e.g., bge-small-en / bge-small-zh via ONNX for offline, cloud API for higher quality when permitted).
  • Language detection from lang attribute — no heuristic guessing.
  • Block-level granularity: one embedding vector per data-opaline-block, not per document.
  • Rebuild command that walks all blocks, regenerates embeddings, and atomically swaps the index.

Publishing Stages

Static Export

Generate a static website from selected notes. This can work without accounts or hosting through GitHub Pages, Cloudflare Pages, Vercel, or a personal server.

Hosted Publish

Opaline or another service may host public notes at a URL like opaline.site/username. This adds accounts, billing, domains, privacy, and content operations.

Public Knowledge Network

Later, public notes from many users could become discoverable through author pages, public note search, collections, citations, follows, bookmarks, cross-user references, and topic discovery.

Reader-Facing Concept Search

A future published Opaline site should let readers select text and search the author's public notes.

Reader selects "HTML-native notes"
  -> Search this note
  -> Search this author
  -> Find related public notes
  -> Ask with cited sources

This is different from ordinary site search. It lets readers treat an author's public knowledge base as a context they can query while reading.

The careful version should be triggered by selection, search only public content unless the reader is authenticated, show source snippets, link to original notes, clearly label AI summaries, and avoid presenting AI inference as the author's direct claim.
