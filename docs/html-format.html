HTML Format and Multilingual Notes

中文概要

这一页说明为什么 Opaline 选择 HTML，以及 HTML 对多语言的支持方式。HTML 本身对中文、英文、阿拉伯文等混排支持很好，关键是统一使用 UTF-8，并正确保留 lang 和 dir 这类语言元数据。

真正的挑战不是 HTML 能不能表达多语言，而是 Opaline 的编辑器、导入导出、搜索和 AI 检索流程能不能稳定保留这些语义。

  • HTML 是发布格式，也是可被浏览器直接打开的文档格式。
  • Opaline 需要限制 HTML 子集，避免保存脏的编辑器输出。
  • data-opaline-* 属性用于保存链接、标签、块、概念等应用语义。
  • 多语言笔记应该允许整篇文档、局部段落甚至引用块分别声明语言。

因此，Opaline 的优势不是“使用 HTML”，而是维护一套适合长期知识管理的干净 HTML Profile。

Why HTML

HTML is not the goal by itself. The goal is durable rich knowledge. HTML is useful because it is readable, publishable, structured, AI-friendly, interaction-friendly, multilingual, and portable.

Markdown is excellent for plain-text notes. Opaline's bet is that long-term knowledge work often wants richer structure than Markdown can express without many incompatible extensions.

Markdown's Ceiling, HTML's Baseline

The difference is easiest to see with concrete examples. Here are things that are natural in HTML and impossible (or fragile) in Markdown:

Bilingual inline annotations

<!-- Markdown: no way to mark language per paragraph -->
This is English.
这是中文。

<!-- HTML: each section declares its language -->
<p lang="en">This is English.</p>
<p lang="zh-Hans">这是中文。</p>

The difference: with HTML, a search engine can limit results to one language. A spellchecker won't flag Chinese characters as English typos. An AI embedding model can route each passage to the right language pipeline. Markdown can't express any of this.

Stable references to a specific paragraph

<!-- Markdown: headings get auto-slugs, but paragraphs have no identity -->
## Database Choice          <!-- slug becomes #database-choice -->
We chose PostgreSQL.         <!-- no way to link here directly -->

<!-- HTML: every block can carry a stable ID -->
<section id="b-db-choice" data-opaline-block>
  <h2>Database Choice</h2>
  <p id="b-db-reason" data-opaline-block>We chose PostgreSQL.</p>
</section>

The id survives: renaming the heading, reordering sections, even moving the paragraph to a different note. Markdown block references break under any of these changes.

Definition lists and semantic associations

<!-- HTML: native definition list -->
<dl>
  <dt>PostgreSQL</dt>
  <dd>Chosen for its JSONB support and mature query planner.</dd>
  <dt>SQLite</dt>
  <dd>Used for local indexes, not for shared data.</dd>
</dl>

<!-- Markdown: no equivalent — you hack it with bold + paragraph or raw HTML -->

Disclosure widgets for progressive detail

<!-- HTML: native collapsible section -->
<details>
  <summary>Why we rejected MongoDB</summary>
  <p>Three reasons: write consistency, query complexity, and operational overhead.</p>
</details>

<!-- Markdown: no native equivalent — Obsidian callouts don't collapse -->

Multilingual Support

HTML has strong multilingual support when documents are saved as UTF-8 and correctly annotated.

  • <meta charset="utf-8"> supports Chinese, English, Japanese, Korean, Arabic, emoji, symbols, and mixed scripts.
  • The lang attribute identifies the language of the document or a specific section.
  • The dir attribute supports left-to-right and right-to-left writing systems.
  • Different sections can use different languages in the same note.
  • Browsers, screen readers, search engines, and spellcheckers can use language metadata.

Example:

<html lang="zh-Hans">
  <body>
    <article data-opaline-note>
      <h1>HTML 笔记</h1>
      <p>这是一段中文。</p>
      <p lang="en">This sentence is in English.</p>
      <p lang="ar" dir="rtl">هذه فقرة عربية.</p>
    </article>
  </body>
</html>

The main challenge is not whether HTML supports languages. It does. The challenge is making Opaline preserve language metadata during editing, import, export, search, and AI retrieval.

Opaline HTML Profile

Opaline should define a strict, predictable subset of HTML instead of saving arbitrary editor output.

  • Use semantic elements where possible.
  • Normalize pasted content.
  • Preserve meaningful lang and dir attributes.
  • Remove editor-only classes and unstable inline styles.
  • Use data-opaline-* attributes for app-specific meaning.
  • Serialize documents consistently for Git-friendly diffs.

Base Note Structure

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <title>Example Note</title>
    <meta name="opaline:id" content="note-id">
    <meta name="opaline:created" content="2026-05-13T00:00:00Z">
    <meta name="opaline:updated" content="2026-05-13T00:00:00Z">
  </head>
  <body>
    <article data-opaline-note>
      <h1>Example Note</h1>
      <p>This is a portable HTML note.</p>
    </article>
  </body>
</html>

Links, Tags, and Blocks

<a href="../projects/opaline.html" data-opaline-link="note-id" data-opaline-link-kind="note">Opaline</a>
<a href="../projects/opaline.html#b-introduction" data-opaline-link="note-id" data-opaline-link-kind="block" data-opaline-block-id="b-introduction">introduction block</a>
<a href="opaline://concept/RAG" data-opaline-link-kind="concept" data-opaline-concept="RAG">RAG</a>

<span data-opaline-tag="research">#research</span>

<section id="b-introduction" data-opaline-block>
  <h2>Introduction</h2>
  <p>...</p>
</section>

Controlled Widgets

Opaline can store future live components as custom elements while keeping the note readable outside the app. The current allowed model is deliberately small: known built-ins such as query, chart, and local-graph may be rendered by Opaline, but note-authored JavaScript is not allowed.

<opaline-widget type="local-graph" title="Current note neighborhood">
  Opaline widget: Current note neighborhood
</opaline-widget>

If the widget is unsupported or opened in a normal browser, the fallback text remains visible. Data should live in attributes or readable child content, not hidden script blocks.
