HTML 格式和多语言笔记

为什么选择 HTML

HTML 本身不是目标。目标是持久且丰富的知识。HTML 之所以有用，是因为它可阅读、可发布、结构清晰、AI 友好、交互友好、支持多语言且可移植。

Markdown 在纯文本笔记方面很出色。Opaline 的赌注是，长期知识工作往往需要比 Markdown 更丰富的结构，而 Markdown 在不引入大量互不兼容扩展的情况下难以表达这些结构。

因此，Opaline 的优势不是"使用 HTML"，而是维护一套适合长期知识管理的干净 HTML Profile。

Markdown 的天花板，HTML 的地板

用具体例子最容易看清差距。以下是 HTML 天然能做、Markdown 做不到（或做起来很脆弱）的事：

双语内联标注

<!-- Markdown：无法按段落标注语言 -->
This is English.
这是中文。

<!-- HTML：每个段落声明自己的语言 -->
<p lang="en">This is English.</p>
<p lang="zh-Hans">这是中文。</p>

差别在于：HTML 可以让搜索引擎把结果限定在一种语言。拼写检查器不会把中文字符标成英文拼写错误。AI 嵌入模型可以把每个段落路由到正确的语言处理管道。Markdown 表达不了这些。

稳定引用某个段落

<!-- Markdown：标题有自动 slug，但段落没有身份 -->
## 数据库选型              <!-- slug 变成 #数据库选型 -->
我们选了 PostgreSQL。       <!-- 没办法直接链接到这里 -->

<!-- HTML：每个块都可以带稳定 ID -->
<section id="b-db-choice" data-opaline-block>
  <h2>数据库选型</h2>
  <p id="b-db-reason" data-opaline-block>我们选了 PostgreSQL。</p>
</section>

id 在重命名标题、调整段落顺序、甚至把段落移到另一篇笔记后仍然有效。Markdown 的块引用在以上任何变动下都会断掉。

定义列表和语义关联

<!-- HTML：原生定义列表 -->
<dl>
  <dt>PostgreSQL</dt>
  <dd>选择原因：JSONB 支持和成熟的查询规划器。</dd>
  <dt>SQLite</dt>
  <dd>本地索引用，不存共享数据。</dd>
</dl>

<!-- Markdown：没有等价物——用粗体加段落凑合，或直接写 raw HTML -->

折叠部件，渐进展开细节

<!-- HTML：原生可折叠区域 -->
<details>
  <summary>为什么不用 MongoDB</summary>
  <p>三个原因：写入一致性、查询复杂度和运维开销。</p>
</details>

<!-- Markdown：没有原生等价物——Obsidian callouts 也不支持折叠 -->

多语言支持

当文档以 UTF-8 保存并正确标注时，HTML 具有强大的多语言支持能力。

  • <meta charset="utf-8"> 支持中文、英文、日文、韩文、阿拉伯文、emoji、符号和混合文字。
  • lang 属性标识文档或特定章节的语言。
  • dir 属性支持从左到右和从右到左的书写系统。
  • 同一篇笔记中不同章节可以使用不同语言。
  • 浏览器、屏幕阅读器、搜索引擎和拼写检查器都可以利用语言元数据。

示例：

<html lang="zh-Hans">
  <body>
    <article data-opaline-note>
      <h1>HTML 笔记</h1>
      <p>这是一段中文。</p>
      <p lang="en">This sentence is in English.</p>
      <p lang="ar" dir="rtl">هذه فقرة عربية.</p>
    </article>
  </body>
</html>

真正的挑战不是 HTML 能不能支持多语言——它完全可以。挑战在于让 Opaline 在编辑、导入、导出、搜索和 AI 检索过程中稳定保留这些语言元数据。

Opaline HTML Profile

Opaline 应该定义一套严格、可预测的 HTML 子集，而不是保存编辑器输出的任意内容。

  • 尽可能使用语义化元素。
  • 规范化粘贴内容。
  • 保留有意义的 lang 和 dir 属性。
  • 移除编辑器专用类名和不稳定的内联样式。
  • 使用 data-opaline-* 属性保存应用级语义。
  • 以 Git 友好的 diff 方式一致地序列化文档。

基础笔记结构

<!doctype html>
<html lang="zh-Hans">
  <head>
    <meta charset="utf-8">
    <title>示例笔记</title>
    <meta name="opaline:id" content="note-id">
    <meta name="opaline:created" content="2026-05-13T00:00:00Z">
    <meta name="opaline:updated" content="2026-05-13T00:00:00Z">
  </head>
  <body>
    <article data-opaline-note>
      <h1>示例笔记</h1>
      <p>这是一篇可移植的 HTML 笔记。</p>
    </article>
  </body>
</html>

活组件与插件策略

Opaline 可以把活组件保存为自定义元素，同时让笔记在应用之外仍然可读。设置页把内置组件、已安装插件组件和实验性脚本笔记分开。

内置组件包括 query、chart、local-graph。第三方组件脚本放在工作区插件文件夹里，例如 .opaline/plugins/network-tools/；笔记文件只保存参数声明。

<opaline-widget type="local-graph" title="当前笔记邻域">
  Opaline widget: 当前笔记邻域
</opaline-widget>

<opaline-widget type="network-status" target="192.168.1.1" endpoint="/status" profile="onu-readonly" refresh="5s">
  Opaline widget: 网络设备状态
</opaline-widget>

<opaline-script title="实验脚本" language="javascript">
  const status = await opaline.net.fetch("http://192.168.1.1/status");
</opaline-script>

如果组件类型没有对应的已安装插件脚本，fallback 文本仍可见。插件用 manifest.json 把组件类型映射到脚本文件；脚本可用 widget 读取参数，并用 opaline.render()、opaline.net.fetch()、opaline.every() 更新输出。保存后的 HTML 会嵌入当前已安装插件脚本副本，直接用浏览器打开也会尝试运行，但浏览器请求仍受 CORS 限制。
