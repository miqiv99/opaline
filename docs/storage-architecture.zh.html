存储模型和架构

工作区模型

桌面端默认会在系统文档目录下创建 Opaline 工作区。用户可以在设置页更改位置；后续需要补迁移流程，在更改位置时把旧工作区文件复制或移动到新位置。

MyNotes/
  notes/
    index.html
    projects/
      opaline.html
  assets/
    images/
    files/
  .opaline/
    index.sqlite
    settings.json
    cache/
    history/
  • notes/ 保存用户创作的持久 HTML 笔记。
  • assets/ 保存图片和附件。
  • .opaline/ 保存可重建的应用元数据、缓存、设置和本地历史。
  • 删除 .opaline/index.sqlite 不应导致用户内容丢失。
  • 工作区应该在普通文件浏览器中保持可查看。
  • 工作区位置属于用户设置，不应该成为首次启动门槛。

存储原则

HTML 文件是规范数据源。SQLite 是有用的、快速的、可重建的。

本地历史版本

Opaline 内置本地历史，用于从误改、误删、重命名和移动等操作中恢复。它不是 Git，也不需要用户安装 Git。快照位于 .opaline/history/，不会污染 notes/，也不会被当成用户主动写作的笔记。

.opaline/
  history/
    {note_id}/
      {timestamp}.html

第一版默认保留最近 30 天。新建笔记会保存初始快照；手动保存时如果内容和上一个快照不同，会保存新快照；删除、重命名、移动前会先保存快照。恢复历史版本时，Opaline 会先为当前版本再创建一份快照，然后用选中的 HTML 覆盖当前笔记，并重建 SQLite 索引。

Git 以后可以作为高级可选工作流，但不是基础用户的历史版本路径。

文件系统保存持久内容

  • HTML 笔记
  • 图片
  • 附件
  • 导出的资源

SQLite 保存派生数据

  • 搜索索引
  • 反链
  • 出链
  • 关系类型和块引用元数据
  • 标签
  • 标题和别名
  • 最近笔记
  • 收藏
  • 工作区设置
  • AI 嵌入向量（如果启用）
  • 缓存元数据

身份模型

Opaline 应该区分身份和位置。

  • 笔记 ID 应该是稳定的 UUID 风格标识符。
  • 路径是面向用户的位置，可能会改变。
  • 链接应同时保存 href 和稳定的 Opaline 目标 ID。
  • 链接还应该保存或推导关系类型：文件级、标题级、块级、概念级。
  • SQLite 可以解析 ID、路径、标题、别名、反链和断链。

架构：两个阶段

架构从纯本地起步，服务端组件只在后续阶段引入。本地是地基，服务端是叠加层。

Phase 0–3：纯本地核心

React UI
  -> 编辑器层
  -> 领域层
  -> 存储适配器
      -> Tauri 桌面文件系统
      -> Tauri 移动文件系统
      -> Web IndexedDB 或 OPFS

一切跑在用户机器上。编辑、保存、搜索、链接不需要网络。FTS5 和 sqlite-vec 在进程内运行。ONNX 在 CPU 上跑嵌入模型。离线状态下应用完全可用。

Phase 5+：服务端叠加

                                    ┌──────────────────────────┐
用户机器（主）                        │ Opaline 服务（叠加层）     │
                                    │                            │
  HTML 笔记  ────────────────→     │  静态站点生成              │
  SQLite 索引（只读副本）────→      │  托管发布                  │
  选定的公开笔记 ────────────→     │  公开笔记搜索              │
                                    │  可选同步                  │
  ← 发布站点预览                     │  面向读者的 AI             │
  ← 公开知识发现                     │  跨用户引用                │
                                    │  账号和计费                │
                                    └──────────────────────────┘

服务端只为天然跨越单机边界的功能而存在：发布到 URL、让读者搜索公开笔记、跨设备同步、发现其他作者的知识。服务端不会取代或降级本地体验。

两个阶段共守的规则

  • HTML 文件永远是规范数据源——不是数据库，也不是服务器。
  • 本地应用的核心功能（编辑、保存、搜索、链接）在无网络时必须完全可用。
  • 服务端索引是由已发布的 HTML 文件派生出来的，绝不可能反过来。
  • 一个从不发布、从不同步、从不用 AI 的用户，使用本地工具时不应损失任何价值。

插件架构：初步方向

Opaline 应该从架构上为插件留出空间，但早期版本不需要立刻做完整的公开插件市场。更合适的路线是先让核心功能内部插件化，等编辑器、存储模型和笔记格式稳定后，再开放稳定的第三方插件 API。

当前架构可以支持插件，前提是插件通过受控的应用 API 工作，而不是直接操作文件系统、SQLite 表结构或编辑器内部状态。

活组件也应该遵守同样边界。笔记可以保存可读的 <opaline-widget> 元素，但渲染应由已知内置组件或未来带权限的插件完成。笔记本身不能执行任意脚本。

两层插件

  • 应用插件：使用 JavaScript 或 TypeScript 编写，用于命令、编辑器行为、侧边栏、导入导出、搜索 provider 和 AI provider。
  • 原生插件：使用 Tauri 或 Rust 扩展真正需要系统能力的功能，例如全局快捷键、托盘、高级文件监听、OCR、本地模型运行时或移动端分享入口。

应用插件应该是主要生态。原生插件要更谨慎，因为它会影响打包、安全、签名和跨平台兼容。

可能的插件类型

  • 编辑器插件：Tiptap 扩展、callout、数学公式、表格、代码高亮、自定义块。
  • 命令插件：命令面板动作，例如总结笔记、清理粘贴 HTML、创建索引页。
  • UI 插件：侧边栏面板、状态栏项目、右键菜单项和笔记检查器。
  • 导入导出插件：Markdown 导入、HTML 清洗、静态站点导出、PDF 导出和迁移工具。
  • 搜索和 AI 插件：嵌入向量 provider、本地模型适配器、云模型适配器、语义搜索 provider 和带引用的 AI 工作流。

受控插件 API

  • workspace：列出笔记、读取笔记、创建笔记，并通过领域层操作更新笔记。
  • editor：注册 Tiptap 扩展、读取当前选区、执行编辑器命令、转换当前笔记。
  • commands：注册和执行命令面板动作。
  • ui：注册侧边栏面板、右键菜单项和状态栏项目。
  • search：执行搜索，并注册可选搜索 provider。
  • ai：注册 AI provider，并执行用户确认过的带引用 AI 工作流。

插件安全规则

  • 插件不应获得直接 SQLite 访问权限。
  • 插件不应获得无限制文件系统访问权限。
  • 插件默认不应执行 shell 命令。
  • 插件不应静默上传 workspace 内容。
  • 插件渲染的组件在插件缺失时，应降级为可读 HTML。
  • 批量修改笔记应可预览、可撤回，或需要用户明确确认。
  • AI 插件应该清楚区分原始笔记内容和模型生成建议。

比较好的早期实现路线，是先把内部功能做成插件：反链、日记、Markdown 导入、HTML 清洗、AI 笔记总结，都可以走同一套注册机制。这样能先用真实功能测试插件 API，再开放给第三方开发者。

各层职责

笔记格式层

  • 解析 HTML
  • 序列化 HTML
  • 规范化保存的文档
  • 验证 Opaline HTML Profile
  • 迁移旧版本笔记

领域层

  • 笔记身份
  • 笔记元数据
  • 链接和反链
  • 标签
  • 资源管理
  • 搜索索引
  • 发布元数据

编辑器层

  • Tiptap 扩展
  • 编辑命令
  • 粘贴净化
  • 选区行为
  • 富块编辑
  • 撤销和重做行为

这套设计的核心是信任：用户内容属于文件系统，数据库只是让体验更快、更聪明。
