搜索、AI 和发布

当前 AI 入口

当前版本先把 AI 分成两个入口：一个是“今天”记录，它把用户随手说的话先写入当天 HTML 今日记录，再让 AI 接着回应；另一个是笔记侧栏里的摘要、标题和标签建议。

模型配置不直接暴露在笔记侧栏，而是放在设置页中。设置页支持 provider、自定义 API 地址、模型、API Key、显式保存、模型连通性测试和抓取模型列表。

这意味着 AI 不是纯聊天壳：用户的原始表达先成为本地文件，AI 回复只是围绕这份本地记录继续展开。

AI 编辑工具协议

编辑器现在有一套统一命令注册表，工具栏、右键菜单、slash 命令、命令面板和未来 AI 生成笔记流程都应该调用同一层。AI 应该拿到工具描述，而不是直接接触编辑器内部状态。

  • 每个命令都有 id、本地化标题和描述 key、分类、分组、图标 key、快捷键元数据、可用性检查、可选 payload schema、UI 可见性元数据和 AI 元数据。
  • AI 可见元数据会标明命令是否修改笔记、需要什么权限、是否需要用户确认、是否应该先创建历史快照，以及是否高风险或实验性。
  • AI 操作计划可以先预览，预览会显示操作明细、未知命令、不可暴露给 AI 的命令、高风险或实验性命令，以及是否会修改本地笔记。
  • 执行前会校验 payload schema，可要求用户确认会修改笔记的计划，可以先创建本地历史快照；如果某个命令失败，可以恢复执行前的编辑器 HTML。

这只是基础设施，不代表 AI 可以静默重写笔记。用户确认、来源展示和本地历史仍然是安全边界的一部分。

在语义搜索之前：关键词搜索已经够好了

一个合理的问题：如果 SQLite FTS5 能在几毫秒内搜索几千篇笔记，而且笔记是我自己写的，我大概率记得关键词——那还要嵌入向量和 AI 搜索干什么？

对个人使用来说，带过滤的关键词搜索被低估了：

  • 记得项目名 → 标题搜索瞬间找到。
  • 记得技术术语 → FTS5 正文搜索亚毫秒级。
  • 大概记得什么时候写的 → 时间范围过滤缩小到 5 个候选。
  • 记得它链接了另一篇笔记 → “谁提到本篇”直接浮现。

关键词搜索的天花板出现在以下场景：

  • 你记得结论但忘了当时用的词。（"那篇为什么选 Postgres 而不是 MySQL 的笔记"——但笔记里从没出现"选"或"而不是"。）
  • 几年前写的东西，用词习惯已经变了。
  • 别人在搜你发布的公开笔记，不知道你的命名习惯。

这就是为什么路线图把语义搜索排在关键词搜索之后，把面向读者的概念搜索排得更靠后。二八原则是：关键词搜索给自己用，语义搜索做关键词找不到时的 fallback，RAG 是发布后给读者用的杀手功能。

搜索应该帮助用户找回旧上下文，而不仅仅是匹配关键词。

精确搜索

跨标题、章节、正文、标签和路径的快速本地关键词搜索。这是增强版的 Ctrl+F 层。

结构化搜索

按路径、标签、笔记类型、创建时间、更新时间、链接笔记和断链进行过滤。

语义搜索

可选的 AI 或嵌入向量驱动的本地笔记检索。结果应该在生成任何回答之前先展示匹配的笔记和片段。

AI 回答

AI 应该只在有可见来源的情况下回答。

  • 引用笔记
  • 链接回原文
  • 展示检索到的片段
  • 当没有找到相关笔记时明确说明
  • 区分来源事实和 AI 推断

私有笔记不应该在未经用户明确许可的情况下发送到云端模型。

RAG 架构和要避的坑

Opaline 的格式给了 RAG 一个结构性的先发优势：每个块已经有稳定 ID、语言元数据和语义元素类型。但纸上看着干净的架构，实现时仍然有真实的坑。这一节把它们记录下来，目的是提前规避，而不是做到一半才发现。

为什么 Opaline 格式对 RAG 有利

  • 块是预分好的。一个 <section data-opaline-block> 或 <p id="..."> 就是一个作者自己定义的检索单元。作者定义边界的效果，比任何算法分块都好。
  • 稳定 ID 在编辑后仍存活。笔记重组时，块 ID 跟着内容走。引用不会漂移。
  • 语言元数据路由嵌入模型。lang="zh" 的块走中文优化的嵌入模型，lang="en" 的块走英文的。混用语言生成一个嵌入向量会降低检索质量。
  • 标签和链接提供结构化预过滤。在向量搜索之前，按标签或链接笔记过滤，先把候选集砍掉 90%。这比在整个工作区做纯向量搜索更快更准。

坑 1：块大小失控

如果 data-opaline-block 被定义为"一个检索单元"，那块的大小直接决定检索质量。一个 5000 字的块什么都能匹配到，但什么都回答不了。一个单句块丢失了周围上下文。这个规则必须早定：一个块包含一个可独立回答的想法——通常在 50 到 300 字之间。编辑器应该对超大块和超小块给出提示（有意为之的一句话定义除外）。

坑 2：嵌入模型锁定

嵌入向量跟模型绑定。从 text-embedding-3-small 换成 bge-m3，所有已有向量变成废品——它们是不同几何空间里的坐标。因为嵌入存在 SQLite 里且标记为可重建，这不是灾难。但重建成本是真实的：一万个块 × API 延迟，不是瞬间能完成的。从第一天起就规划好"重建全部嵌入"的命令，并优先选择长期稳定可用的嵌入模型。

坑 3：隐私与云端的边界

嵌入生成和回答生成是两个独立步骤，但两者都可能访问云端 API。标记为私有的笔记，用户必须能信任其内容不会离开本机。这意味着：

  • 嵌入必须支持纯本地模式（例如通过 ONNX 运行 bge-small，使用 sqlite-vec 或 fastembed）。
  • AI 回答生成要么完全本地运行，要么在把检索到的私有片段发送到云端模型之前明确提示用户。
  • 隐私边界必须在 UI 中可见——标记为私有的笔记应显示清晰的"已排除云端操作"标识。

坑 4：笔记移动导致引用断链

块 ID 如 b-db-choice 在笔记内部是稳定的。但如果笔记被重命名或移动，指向它的链接中的 href 路径就断了。ID 仍然有效，但 URL 不在了。这意味着引用必须通过 ID 查找来解析（SQLite 解析 ID → 当前路径），而不是依赖原始 href。每条 AI 引用都应该把块 ID 作为规范引用存储，显示路径在渲染时动态解析。

坑 5：混合搜索不可省略

纯向量搜索会产生看起来通顺但内容上错误的答案，频率高到足以侵蚀信任。比如"PostgreSQL JSONB 性能"这个查询，应该匹配字面上包含这些术语的块，而不是语义上相邻的块。检索管道必须组合：

  • 关键词匹配（FTS5）保证已知术语的精确性。
  • 向量相似度保证概念匹配的召回率。
  • 元数据过滤（标签、日期、链接）在以上两者之前先执行。
  • 对合并结果重新排序后再送入 LLM。

坑 6：重排序的成本不可忽略

检索可能返回 50 个候选块。大多数 LLM 上下文窗口塞不进 50 个块外加用户问题和回答。需要一个重排序器（交叉编码器或更小的模型）把候选块裁到前 5–10 个，再生成最终答案。这一步在原型阶段很容易被跳过，但一上生产就立刻需要。

Phase 5 推荐技术栈

  • sqlite-vec 用于向量存储，与 FTS5 共处同一个 SQLite 数据库。
  • 稳定的嵌入模型配本地 fallback（例如 ONNX 运行 bge-small-zh / bge-small-en 做离线模式，允许时用云端 API 获取更高质量）。
  • 语言检测从 lang 属性读取——不做启发式猜测。
  • 块级粒度：每个 data-opaline-block 一个嵌入向量，而非每篇文档一个。
  • 重建命令：遍历所有块，重新生成嵌入，原子性地替换索引。

发布阶段

静态导出

从选定笔记生成静态网站。这可以通过 GitHub Pages、Cloudflare Pages、Vercel 或个人服务器实现，无需账号或托管服务。

托管发布

Opaline 或其他服务可以在 opaline.site/用户名 这样的 URL 托管公开笔记。这会涉及账号、计费、域名、隐私和内容运营。

公开知识网络

后续，来自许多用户的公开笔记可以通过作者页面、公开笔记搜索、合集、引用、关注、书签、跨用户引用和话题发现变得可被发现。

面向读者的概念搜索

未来发布的 Opaline 站点应该让读者选中文本后可以搜索作者的公开笔记。

读者选中 "HTML 原生笔记"
  -> 搜索本篇笔记
  -> 搜索该作者
  -> 查找相关公开笔记
  -> 带引用来源提问

这与普通的网站搜索不同。它让读者把作者的公开知识库当作可以在阅读时查询的上下文。

谨慎的做法应该是：由选中文本触发、只搜索公开内容（除非读者已认证）、显示来源片段、链接到原始笔记、清晰标注 AI 摘要、避免将 AI 推断呈现为作者的直接主张。
