Vision and Positioning

中文概要

这一页说明 Opaline 的产品定位：它首先是一个本地优先的个人知识工具，而不是论坛、平台或完整复制 Obsidian。核心闭环是写下来、存得住、找得到、连得上、以后能发布。

第一用户是作者。公开笔记、读者搜索、AI 追问和 Diandanr 打通都是长期方向，应该建立在本地 HTML 知识系统足够可靠之后。

  • 短期目标：让个人能放心把真实笔记交给 Opaline。
  • 中期目标：让笔记能被搜索、链接、整理和 AI 检索。
  • 长期目标：让公开笔记成为可阅读、可引用、可追问的知识网络。

这意味着 Opaline 的第一性问题不是“能做多少功能”，而是“能不能长期保存和理解用户自己的知识”。

Opaline is a local-first knowledge workspace built around clean HTML as the native note format.

It starts as a personal desktop note app, but the larger idea is broader: notes should be durable local documents that can be edited comfortably, searched deeply, linked together, published as webpages, and eventually queried by AI with clear citations.

Core Thesis

Obsidian proved that local Markdown files can become a serious personal knowledge base. Opaline explores a related but different bet:

Rich knowledge notes should be stored as clean local HTML, so every note is already a readable document, a publishable webpage, and a structured source for AI-assisted organization.

Why Not Markdown

If Markdown already works for personal knowledge — Obsidian proved it does — why build on HTML?

The short answer: Markdown is a writing shorthand. HTML is a document format. When your notes stay small and single-language, the difference doesn't matter. When they grow complex, the gap widens.

Things HTML can express natively that Markdown cannot (or can only do with incompatible extensions):

Language boundaries

In HTML, a paragraph knows what language it is: <p lang="zh">中文</p><p lang="en">English</p>. In Markdown, two adjacent paragraphs are just text. No parser can tell which is which. This matters for bilingual search ("search only my English notes"), spellcheck, screen readers, and AI retrieval that needs to know the language of a passage before embedding it.

Stable block identity

HTML allows every section to carry a persistent ID: <section id="b-db-choice" data-opaline-block>. You can link to it, it survives reordering and editing, and backlinks resolve correctly. Markdown has no concept of block identity — block references rely on fragile text matching or auto-generated slugs that break when headings change.

Rich document primitives

Definition lists, figure captions, asides, disclosure widgets — <dl>, <figure>, <aside>, <details> are standard HTML. In Markdown, each of these needs a different plugin or raw HTML escape hatch.

Round-trip without loss

Markdown → HTML → Markdown is lossy. Which flavor? Which extensions? Did you write --- as a horizontal rule or YAML frontmatter? HTML → edit → HTML has no conversion step, so nothing is lost.

None of this means Markdown is bad. It means Markdown is optimized for writing, while HTML is optimized for being the document. Opaline bets that for long-term knowledge, the document format matters more than the typing shorthand.

Relationship to Obsidian

Obsidian proved the market: local files, wiki-links, and a plugin ecosystem can become a serious knowledge tool. Opaline is not trying to beat Obsidian at its own game.

The difference is structural:

  • Obsidian builds on Markdown and extends it with plugins (Dataview for queries, Callouts for admonitions, Canvas for visual layouts). These are well-executed workarounds — but they are workarounds for a format that wasn't designed for rich structure.
  • Opaline bets that starting from a richer format lets the core do more without plugins: no Dataview needed when structured metadata is native HTML, no Callout syntax when <aside> exists, no Canvas JSON when blocks already have IDs that can be arranged.

The real question for an Obsidian user is not "should I switch" — it's "is my knowledge work complex enough that Markdown's ceiling is starting to matter." Opaline is for people who feel that ceiling.

The first user is the author, not the public reader. Opaline should serve people who accumulate knowledge over time: researchers, writers, developers, students, product thinkers, and technical creators.

First Product Loop

write -> save -> search -> link -> organize -> publish later

The long-term direction can grow toward public knowledge sites and reader-facing AI search, but only after the local knowledge system is trustworthy.

Product Principles

  • Local-first by default.
  • HTML files are the source of truth.
  • SQLite indexes are rebuildable.
  • Notes should remain useful without Opaline installed.
  • The editor should feel fast, calm, and serious.
  • Search should help users recover old context, not only match keywords.
  • AI should propose, explain, and cite. It should not silently rewrite knowledge.
  • Publishing should be a natural consequence of the file format, not the first product.
  • Public and community features should come after the personal tool is solid.
  • When server-side features arrive (publishing, sync, public search), the local core must remain fully functional without them. Local is the foundation, server is additive.

Relationship to Diandanr

Opaline and Diandanr can eventually complement each other, but should remain separate for now.

Opaline  = local knowledge creation and management
Diandanr = publishing, site generation, distribution, and platform features
