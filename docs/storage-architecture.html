Storage and Architecture

中文概要

这一页说明 Opaline 的本地存储和架构分层。HTML 文件是用户内容的真实来源，SQLite 只保存索引、反链、标签、最近访问、搜索缓存和可重建的派生数据。

架构上应该把编辑器层、领域层、格式层和存储适配器分开。Tiptap 是实现细节，Opaline HTML 格式应该比具体编辑器更长寿。

  • notes/ 保存用户真正的 HTML 笔记。
  • assets/ 保存图片和附件。
  • .opaline/ 保存 SQLite、缓存和设置。
  • 删除 SQLite 不应该导致笔记丢失，只需要重新扫描即可恢复索引。

这套设计的核心是信任：用户内容属于文件系统，数据库只是让体验更快、更聪明。

Workspace Model

MyNotes/
  notes/
    index.html
    projects/
      opaline.html
  assets/
    images/
    files/
  .opaline/
    index.sqlite
    settings.json
    cache/
  • notes/ stores durable user-authored HTML.
  • assets/ stores images and attachments.
  • .opaline/ stores rebuildable app metadata and cache.
  • Deleting .opaline/index.sqlite should not destroy user content.
  • The workspace should remain inspectable in normal file browsers.

Storage Rule

HTML files are canonical. SQLite is useful, fast, and rebuildable.

Files Store Durable Content

  • HTML notes
  • images
  • attachments
  • exported assets

SQLite Stores Derived Data

  • search index
  • backlinks
  • outgoing links
  • tags
  • titles and aliases
  • recent notes
  • favorites
  • workspace settings
  • AI embeddings if enabled
  • cached metadata

Identity Model

Opaline should distinguish identity from location.

  • Note IDs should be stable UUID-style identifiers.
  • Paths should be user-facing locations that may change.
  • Links should store both an href and a stable Opaline target ID when possible.
  • SQLite can resolve IDs, paths, titles, aliases, backlinks, and broken links.

Architecture: Two Phases

The architecture starts local-only and grows server-side components only in later phases. Local is the foundation; server is additive.

Phase 0–3: Local-Only Core

React UI
  -> Editor layer
  -> Domain layer
  -> Storage adapter
      -> Tauri desktop file system
      -> Tauri mobile file system
      -> Web IndexedDB or OPFS

Everything runs on the user's machine. No network dependency for editing, saving, searching, or linking. FTS5 and sqlite-vec run in-process. ONNX runs embedding models on CPU. The app is fully functional offline.

Phase 5+: Server-Side Additions

                                    ┌──────────────────────────┐
User Machine (primary)              │ Opaline Services (additive)│
                                    │                            │
  HTML notes  ────────────────→     │  Static site generation    │
  SQLite index (read replica) ──→   │  Hosted publish            │
  Selected public notes ────────→   │  Public note search        │
                                    │  Optional sync             │
  ← Published site preview          │  Reader-facing AI          │
  ← Public knowledge discovery      │  Cross-user references     │
                                    │  Accounts and billing      │
                                    └──────────────────────────┘

The server side exists only for features that inherently cross machine boundaries: publishing to a URL, letting readers search public notes, syncing across devices, and discovering knowledge from other authors. None of it replaces or downgrades the local experience.

Shared Rules Across Both Phases

  • HTML files are always the canonical source of truth — not a database, not a server.
  • The local app must remain fully functional without network access for all core features (edit, save, search, link).
  • Server-side indexes are derived from published HTML files, never the other way around.
  • A user who never publishes, never syncs, and never uses AI should lose no value from the local tool.

Plugin Architecture: Initial Direction

Opaline should be designed so plugins are possible, but the first releases do not need a full public marketplace. The early goal is to make core features internally extensible, then expose a stable third-party plugin API after the editor, storage model, and note format have settled.

The current architecture can support plugins if plugins interact with controlled application APIs instead of directly touching the file system, SQLite schema, or editor internals.

Two Plugin Layers

  • App plugins: JavaScript or TypeScript extensions for commands, editor behavior, side panels, import/export, search providers, and AI providers.
  • Native plugins: Tauri or Rust extensions for capabilities that truly need system access, such as global shortcuts, tray integration, advanced file watching, OCR, local model runtimes, or mobile share targets.

App plugins should be the main plugin ecosystem. Native plugins should remain more restricted because they affect packaging, security, signing, and cross-platform compatibility.

Possible Plugin Types

  • Editor plugins: Tiptap extensions, callouts, math, tables, code highlighting, custom blocks.
  • Command plugins: command palette actions such as summarize note, clean pasted HTML, or create an index note.
  • UI plugins: sidebar panels, status items, context menu entries, and note inspectors.
  • Import/export plugins: Markdown import, HTML cleanup, static site export, PDF export, and migration tools.
  • Search and AI plugins: embedding providers, local model adapters, cloud model adapters, semantic search providers, and citation workflows.

Plugin Manifest Sketch

  "version": "0.1.0",

}

Controlled Plugin APIs

  • workspace: list notes, read notes, create notes, update notes through domain-level operations.
  • editor: register Tiptap extensions, read the current selection, run editor commands, and transform the current note.
  • commands: register and execute command palette actions.
  • ui: register sidebar panels, context menu items, and status items.
  • search: run searches and register optional search providers.
  • ai: register providers and run user-approved AI workflows with citations.

Plugin Safety Rules

  • Plugins should not receive direct SQLite access.
  • Plugins should not receive unrestricted file system access.
  • Plugins should not execute shell commands by default.
  • Plugins should not silently upload workspace content.
  • Bulk edits to notes should be previewable, reversible, or explicitly confirmed.
  • AI plugins should clearly distinguish original note content from model-generated suggestions.

A good early implementation path is to build internal features as plugins first: backlinks, daily notes, Markdown import, HTML cleanup, and AI note summary can all use the same registration system. This tests the plugin API before exposing it to third-party developers.
